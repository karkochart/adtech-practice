## 01. Активные кампании и их активность за последний час

**Условие.** Для **каждой активной** кампании (`campaigns.status = 'active'`) вывести:
`campaign_id`, `name`, `impressions`, `clicks` - число событий типа `impression` и `click` за **последние 60 минут**
относительно `@now` (то есть `created_at > @now - INTERVAL 60 MINUTE`).

- Кампании, у которых за этот период **нет ни одного события**, тоже должны быть в результате, с нулями.
- Сортировка: `impressions` по возрастанию, затем `campaign_id` по возрастанию.
- В ответе только первые **10** строк (`LIMIT 10`).
- Типы: `impressions` и `clicks` - целые числа, не `NULL`.

**Проверка себе.** Без `LIMIT` строк должно быть ровно столько, сколько активных кампаний (`SELECT COUNT(*) FROM campaigns WHERE status='active'` - сейчас 195).
В данных есть 5 новых кампаний (`new-campaign-1..5`), у которых **нет ни одного события** - в правильном ответе они наверху с нулями.

**Файл:** `sql/answers/01.sql` · **Запуск:** `make sql-run F=01`

**Разбор** (решение показано 16.10 - через пару дней решить с нуля, не подглядывая):

```sql
SET @now = (SELECT MAX(created_at) FROM events);
SELECT
    c.id AS campaign_id,
    c.name,
    COUNT(CASE WHEN e.type = 'impression' THEN 1 END) AS impressions,
    COUNT(CASE WHEN e.type = 'click' THEN 1 END) AS clicks
FROM campaigns AS c
LEFT JOIN events AS e
       ON e.campaign_id = c.id
      AND e.created_at > @now - INTERVAL 60 MINUTE
WHERE c.status = 'active'
GROUP BY c.id, c.name
ORDER BY impressions, c.id
LIMIT 10;
```

Ошибки, на которых споткнулись:
1. `now()` вместо `@now` - данные старые, окно от «сейчас» пустое.
2. `COUNT(CASE ... THEN 1 ELSE 0 END)` - `COUNT` считает всё, что не `NULL`, а `0` не `NULL`: получалось «показы = клики = все строки». Нужно без `ELSE` (будет `NULL`) или `SUM(...)` + `COALESCE`.
3. `JOIN` теряет кампании без событий (190 строк вместо 195).
4. При `LEFT JOIN` условие на правую таблицу в `WHERE` снова превращает его в обычный `JOIN`: `NULL > x` не истина. Условия на правую таблицу - в `ON`, на левую - в `WHERE`.
5. `campaign_id` - из `campaigns`, не из `events` (у кампаний без событий там `NULL`).

Для интервью: «условие на присоединяемую таблицу в `WHERE` убивает `LEFT JOIN`» и «`COUNT(expr)` считает не-`NULL`» - классические вопросы.

## 02. Топ-3 кампании по кликам за каждый из трёх последних полных дней

**Условие.** Возьмите три **полных** дня перед днём `@now`: даты с `DATE(@now) - 3` по `DATE(@now) - 1`.
Сам день `@now` не берём - он неполный. Для каждого из этих дней найдите кампании с наибольшим числом **кликов**
(`type = 'click'`). Учитываются все кампании, и активные, и на паузе.

**Место считается «как в спорте»:** одинаковое число кликов - одинаковое место, а следующие места после ничьей
пропускаются: `1, 2, 2, 2, 5, ...`. Выведите всех, у кого место **≤ 3**. Поэтому в одном дне строк может быть больше трёх,
а третьего места может и не оказаться.

- Колонки: `day` (дата), `campaign_id`, `clicks`, `place`.
- Сортировка: `day`, затем `place`, затем `campaign_id` - всё по возрастанию.
- Дополнительно: фильтр по дате напишите так, чтобы он мог использовать индекс по `created_at` (без функции над колонкой).

**Проверка себе.** Всего должно получиться **14 строк**. За `2026-10-12` три кампании делят 2-е место, и 3-го места в этот день нет.

**Вопрос на интервью (ответьте в комментарии в файле).** Сколько строк получилось бы, если вместо вашей функции взять
каждую из `ROW_NUMBER`, `RANK`, `DENSE_RANK`, и почему?

**Файл:** `sql/answers/02.sql` · **Запуск:** `make sql-run F=02`

**Разбор** (16.10). Логика ваша: `RANK()` по дням, клики в `WHERE`, фильтр по дате без функции над колонкой.
Итоговый запрос - в `sql/answers/02.sql`. Что пришлось поправить и что запомнить:

1. **`ORDER BY` - только во внешнем `SELECT`.** Сортировка внутри подзапроса ничего не гарантирует для внешнего результата
   (MySQL может её отбросить или выдать строки в другом порядке при другом плане). На этих данных порядок совпал случайно.
2. **При ничьих нужен тай-брейкер** (`campaign_id`), иначе порядок и даже состав (`ROW_NUMBER`) не определены.
3. **`ROW_NUMBER` / `RANK` / `DENSE_RANK`** на этом запросе: 9 / 14 / 16 строк (подробно - в комментарии в файле).
4. **Окно считается после `WHERE` и `GROUP BY`,** поэтому `place <= 3` фильтруют уровнем выше (подзапрос или CTE).
5. **Правильное условие не равно использованию индекса.** Условие по дате без функции даёт оптимизатору выбрать индекс,
   но за 3 дня из 14 (≈40% таблицы) MySQL выбрал полный просмотр - так дешевле. Решает селективность.
