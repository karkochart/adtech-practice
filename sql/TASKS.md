## 01. Активные кампании и их активность за последний час

**Условие.** Для **каждой активной** кампании (`campaigns.status = 'active'`) вывести:
`campaign_id`, `name`, `impressions`, `clicks` - число событий типа `impression` и `click` за **последние 60 минут**
относительно `@now` (то есть `created_at > @now - INTERVAL 60 MINUTE`).

- Кампании, у которых за этот период **нет ни одного события**, тоже должны быть в результате, с нулями.
- Сортировка: `impressions` по возрастанию, затем `campaign_id` по возрастанию.
- В ответе только первые **10** строк (`LIMIT 10`).
- Типы: `impressions` и `clicks` - целые числа, не `NULL`.

**Проверка себе.** Без `LIMIT` строк должно быть ровно столько, сколько активных кампаний (`SELECT COUNT(*) FROM campaigns WHERE status='active'` - сейчас 195).
В данных есть 5 новых кампаний (`new-campaign-1..5`), у которых **нет ни одного события** - в правильном ответе они наверху с нулями.

**Файл:** `sql/answers/01.sql` · **Запуск:** `make sql-run F=01`

**Разбор:**

```sql
SET @now = (SELECT MAX(created_at) FROM events);
SELECT
    c.id AS campaign_id,
    c.name,
    COUNT(CASE WHEN e.type = 'impression' THEN 1 END) AS impressions,
    COUNT(CASE WHEN e.type = 'click' THEN 1 END) AS clicks
FROM campaigns AS c
LEFT JOIN events AS e
       ON e.campaign_id = c.id
      AND e.created_at > @now - INTERVAL 60 MINUTE
WHERE c.status = 'active'
GROUP BY c.id, c.name
ORDER BY impressions, c.id
LIMIT 10;
```

Ошибки, на которых споткнулись:
1. `now()` вместо `@now` - данные старые, окно от «сейчас» пустое.
2. `COUNT(CASE ... THEN 1 ELSE 0 END)` - `COUNT` считает всё, что не `NULL`, а `0` не `NULL`: получалось «показы = клики = все строки». Нужно без `ELSE` (будет `NULL`) или `SUM(...)` + `COALESCE`.
3. `JOIN` теряет кампании без событий (190 строк вместо 195).
4. При `LEFT JOIN` условие на правую таблицу в `WHERE` снова превращает его в обычный `JOIN`: `NULL > x` не истина. Условия на правую таблицу - в `ON`, на левую - в `WHERE`.
5. `campaign_id` - из `campaigns`, не из `events` (у кампаний без событий там `NULL`).

Для интервью: «условие на присоединяемую таблицу в `WHERE` убивает `LEFT JOIN`» и «`COUNT(expr)` считает не-`NULL`» - классические вопросы.

## 02. Топ-3 кампании по кликам за каждый из трёх последних полных дней

**Условие.** Возьмите три **полных** дня перед днём `@now`: даты с `DATE(@now) - 3` по `DATE(@now) - 1`.
Сам день `@now` не берём - он неполный. Для каждого из этих дней найдите кампании с наибольшим числом **кликов**
(`type = 'click'`). Учитываются все кампании, и активные, и на паузе.

**Место считается «как в спорте»:** одинаковое число кликов - одинаковое место, а следующие места после ничьей
пропускаются: `1, 2, 2, 2, 5, ...`. Выведите всех, у кого место **≤ 3**. Поэтому в одном дне строк может быть больше трёх,
а третьего места может и не оказаться.

- Колонки: `day` (дата), `campaign_id`, `clicks`, `place`.
- Сортировка: `day`, затем `place`, затем `campaign_id` - всё по возрастанию.
- Дополнительно: фильтр по дате напишите так, чтобы он мог использовать индекс по `created_at` (без функции над колонкой).

**Проверка себе.** Всего должно получиться **14 строк**. За `2026-10-12` три кампании делят 2-е место, и 3-го места в этот день нет.

**Вопрос на интервью (ответ - комментарием в файле).** Сколько строк получилось бы, если взять
каждую из `ROW_NUMBER`, `RANK`, `DENSE_RANK`, и почему?

**Файл:** `sql/answers/02.sql` · **Запуск:** `make sql-run F=02`

**Разбор.** Решение: `RANK()` по дням, клики в `WHERE`, фильтр по дате без функции над колонкой.
Итоговый запрос - в `sql/answers/02.sql`. Что пришлось поправить и что запомнить:

1. **`ORDER BY` - только во внешнем `SELECT`.** Сортировка внутри подзапроса ничего не гарантирует для внешнего результата
   (MySQL может её отбросить или выдать строки в другом порядке при другом плане). На этих данных порядок совпал случайно.
2. **При ничьих нужен тай-брейкер** (`campaign_id`), иначе порядок и даже состав (`ROW_NUMBER`) не определены.
3. **`ROW_NUMBER` / `RANK` / `DENSE_RANK`** на этом запросе: 9 / 14 / 16 строк (подробно - в комментарии в файле).
4. **Окно считается после `WHERE` и `GROUP BY`,** поэтому `place <= 3` фильтруют уровнем выше (подзапрос или CTE).
5. **Правильное условие не равно использованию индекса.** Условие по дате без функции даёт оптимизатору выбрать индекс,
   но за 3 дня из 14 (≈40% таблицы) MySQL выбрал полный просмотр - так дешевле. Решает селективность.

## 03. Медленная лента пользователя: подобрать индекс

**Ситуация.** В админке есть экран «последние показы пользователя». Запрос:

```sql
SELECT id, campaign_id, created_at
FROM events
WHERE user_id = 65073 AND type = 'impression'
ORDER BY created_at DESC
LIMIT 20;
```

Сейчас у `events` только первичный ключ, и запрос заметно тормозит.

**Что сделать** (всё - в файле `sql/answers/03.sql`, по шагам из шаблона):
1. `EXPLAIN` и `EXPLAIN ANALYZE` **до** индекса. Выпишите в комментарий: `type`, `rows`, `Extra` и фактическое время.
2. Создайте **один** индекс, после которого в `EXPLAIN`:
   - `type` = `ref` (поиск по индексу, а не просмотр всей таблицы),
   - `rows` - десятки, а не миллионы,
   - в `Extra` **нет** `Using filesort` (сортировка не нужна, строки уже идут по индексу в нужном порядке).
3. `EXPLAIN` и `EXPLAIN ANALYZE` **после**. Выпишите те же показатели.
4. **Бонус:** доведите индекс до **покрывающего** - в `Extra` появится `Using index` (запрос не ходит в саму таблицу).
5. В конце файла **удалите** свой индекс (`ALTER TABLE events DROP INDEX ...`), чтобы файл можно было запускать повторно,
   а таблица оставалась в исходном состоянии для следующих задач.

**Вопросы как на интервью** (ответы - комментариями в файле):
- Почему колонки в индексе именно в таком порядке? Что будет с индексом `(created_at, user_id, type)`?
- Для покрывающего индекса вы, скорее всего, не добавили `id`, хотя он есть в `SELECT`. Почему он всё равно «покрыт»?
- Индекс построен по возрастанию `created_at`, а запрос просит `DESC`. Почему сортировка всё равно не нужна?
- Чем плохо создавать индекс «на всякий случай» на каждую колонку?

**Проверка себе.** Запрос возвращает 20 строк. После индекса `rows` ≈ 49 (столько показов у этого пользователя), время - доли миллисекунды.

**Файл:** `sql/answers/03.sql` · **Запуск:** `make sql-run F=03` · Удобно смотреть планы и в PhpStorm (`adtech@localhost`).

**Разбор.** Индекс: `(user_id, type, created_at, campaign_id)` - сразу и без сортировки, и покрывающий.
Итог в `sql/answers/03.sql`. Что запомнить:

1. **Порядок колонок:** равенства → сортировка или диапазон → колонки «только прочитать». Первый вариант `(user_id, type)`
   нашёл 49 строк, но сортировал их отдельно (`Using filesort`).
2. **Покрывающий индекс** = в индексе есть все колонки запроса, `Extra: Using index`. ≈ 0,075 мс → ≈ 0,02 мс.
3. **Первичный ключ уже есть в каждом вторичном индексе InnoDB** - `id` добавлять не нужно.
4. **`DESC` читается по индексу с конца** (`Backward index scan`).
5. **`EXPLAIN` - это оценка.** С индексом `(created_at, user_id, type)` он обещал `rows = 20`, а реально прочитано
   691 227 записей. Работу проверяют `EXPLAIN ANALYZE` или счётчиками `Handler_read_*` (`FLUSH STATUS` под `root`).
6. **Время повторного запуска обманчиво:** кэша запросов в MySQL 8 нет, но данные «прогреты» в буферном пуле.

## 04. Почасовые клики кампании: пустые часы и самая длинная серия без кликов

**Ситуация.** Для графика в дашборде нужны клики кампании **111** по часам. На графике должны быть **все** часы,
в том числе те, где кликов не было: дыра на оси времени - это ошибка, а не «ноль».

**Условие.** Пусть `@to` - начало часа, в котором находится `@now` (например, `@now = 16:10:55` → `@to = 16:00:00`).
Нужны **48 полных часов перед `@to`**: от `@to - 48 часов` включительно до `@to` не включительно.
Для каждого часа вывести:
- `hour` - начало часа (`DATETIME`, например `2026-10-13 16:00:00`),
- `clicks` - число событий `type = 'click'` кампании 111 за этот час; если кликов не было - `0`, не `NULL`.

Сортировка по `hour`. Ряд часов сгенерируйте **рекурсивным CTE** (`WITH RECURSIVE`), без вспомогательных таблиц.

Подсказка по синтаксису (не по решению): начало часа получается так -
`CAST(DATE_FORMAT(x, '%Y-%m-%d %H:00:00') AS DATETIME)`.

**Проверка себе.** Ровно **48 строк**, первая - `2026-10-13 16:00:00`, последняя - `2026-10-15 15:00:00`, часов с нулём - **19**.
Обычный `GROUP BY` по событиям вернёт только 29 строк - это и есть та «дыра».

**Бонус (классика собеседований, gaps and islands).** Найдите самую длинную серию **подряд идущих** часов без кликов
среди этих 48: `start_hour`, `end_hour`, `hours_without_clicks`. Подсказка-направление: разность двух `ROW_NUMBER()`.

**Вопросы как на интервью** (ответы - комментариями в файле):
- Чем опасен рекурсивный CTE без условия остановки и что делает `cte_max_recursion_depth`?
- Почему ряд часов нельзя получить одним `GROUP BY` по `events`?

**Файл:** `sql/answers/04.sql` · **Запуск:** `make sql-run F=04`

**Разбор.** Основной запрос: ряд часов `WITH RECURSIVE`, `LEFT JOIN` с условиями в `ON`, `COUNT(e.id)` вместо `NULL`.
Итог в `sql/answers/04.sql`. Что запомнить:

1. **Границы окна.** Было `@now - 47 часов` ... час самого `@now`: окно сдвинулось на час и захватило **неполный** текущий час.
   Правильно: считаем `@to` = начало часа `@now` и берём `[@to - 48 ч, @to)` - полуинтервал, без текущего часа.
2. **Типы в сравнении.** `DATE_FORMAT` возвращает строку; сравнение `DATETIME` со строкой работает через неявное приведение,
   но надёжнее один раз сделать `CAST(... AS DATETIME)` в переменную.
3. **Gaps and islands:** `ROW_NUMBER() OVER (ORDER BY t) - ROW_NUMBER() OVER (PARTITION BY признак ORDER BY t)`
   постоянна внутри серии подряд идущих строк с одинаковым признаком. Дальше `GROUP BY` этой разности.
   Рекурсивный счётчик нулей подряд - тоже рабочий способ, но ограничен `cte_max_recursion_depth` (по умолчанию 1000).
4. **Почему нужен ряд часов:** `GROUP BY` по `events` возвращает только часы, где были строки (29 из 48) -
   «пустых» часов в таблице просто нет, их надо сгенерировать и присоединить.

## 05. Индекс есть, а запрос его не использует

**Ситуация.** Индексы на `events` уже созданы (это делает начало шаблона):

```sql
CREATE INDEX idx_created      ON events (created_at);
CREATE INDEX idx_click_id     ON events (click_id);
CREATE INDEX idx_camp_created ON events (campaign_id, created_at);
```

Но четыре запроса из отчётов всё равно медленные. Нужные индексы есть, мешает то, **как написано условие**.
Новые индексы не создавайте, нужно переписать запросы.

```sql
-- A. Сколько событий было за 14 октября
SELECT COUNT(*) FROM events WHERE DATE(created_at) = '2026-10-14';

-- B. Найти клик по его click_id (пришёл из постбэка партнёра)
SELECT id, campaign_id, user_id, created_at FROM events WHERE click_id = 353957;

-- C. События и расход за последний час
SELECT COUNT(*), SUM(cost) FROM events WHERE created_at + INTERVAL 1 HOUR > @now;

-- D. Показы и клики кампании 111 за час 2026-10-15 09:00-09:59
SELECT type, COUNT(*) FROM events
WHERE campaign_id = 111 AND DATE_FORMAT(created_at, '%Y-%m-%d %H') = '2026-10-15 09'
GROUP BY type;
```

**Что сделать** (всё - в файле `sql/answers/05.sql`, по шагам из шаблона):
1. Для каждого запроса - `EXPLAIN` и `EXPLAIN ANALYZE` **как есть**. Выпишите в комментарий: `type`, `key`, `key_len`, `rows`
   и фактическое время.
2. Перепишите каждый запрос так, чтобы он использовал индекс по-настоящему. **Результат должен совпасть до строки** -
   сначала сравните результаты старого и нового варианта, потом планы.
3. `EXPLAIN` и `EXPLAIN ANALYZE` **после**, те же показатели.
4. Индексы в конце шаблона удаляются - не убирайте эти строки, чтобы файл запускался повторно.

**Правила:**
- Без новых индексов и без изменения таблицы.
- Границы периода - полуоткрытый интервал: «с начала, включительно - до конца, не включительно». `BETWEEN ... '23:59:59'`
  не используйте и объясните в комментарии, почему.

- `click_id LIKE '3539%'` и `click_id LIKE '%3957'` - какой из них может искать по индексу и почему?

**Проверка себе.**

**Разбор.** Итоговые запросы, цифры до и после и ответы на вопросы - в `sql/answers/05.sql`.

| | Было | Стало | Время |
|---|---|---|---|
| A | `DATE(created_at) = ...` - читается весь индекс, 2 млн записей | `created_at >= '2026-10-14' AND created_at < '2026-10-15'`, `range` | ≈ 320 → 35 мс |
| B | `click_id = 353957` - `ALL`, `key = NULL` | `click_id = '353957'`, `ref`, `rows = 1` | ≈ 415 → 0,03 мс |
| C | `created_at + INTERVAL 1 HOUR > @now` - `ALL`, `possible_keys = NULL` | `created_at > @now - INTERVAL 1 HOUR`, `range` | ≈ 680 → 17 мс |
| D | `DATE_FORMAT(created_at, ...)` - `key_len = 4`, 18 564 строки | полуоткрытый интервал на час, `key_len = 9`, 33 строки | ≈ 2,5 → 0,1-0,6 мс |

Что запомнить:
1. **Колонка в `WHERE` - «голая»**, всё преобразование - на стороне значения. Функция или арифметика над константой
   считается один раз (`<cache>(...)` в плане), над колонкой - для каждой строки.
2. **Сначала результат, потом план.** `created_at = '2026-10-14'` даёт «идеальный» план (`ref`, `rows = 1`) и ответ 1
   вместо 143 479: это сравнение с одним моментом 00:00:00, а не с днём.
3. **Тип значения = тип колонки.** `VARCHAR = число` сравнивает как числа и конвертирует каждую строку
   (`'0353957'`, `' 353957'`, `'353957abc'` все равны 353957) - индекс невозможен, `FORCE INDEX` не помогает.
   `INT = '111'` безопасно: конвертируется одна константа. В Laravel `int` биндится как `PDO::PARAM_INT`.
4. **`key` не пустой - ещё не всё.** `key_len` показывает, сколько колонок индекса реально участвуют в поиске:
   4 байта = только `campaign_id`, 9 = `campaign_id` + `created_at`.
5. **Периоды - полуоткрытые `[начало, конец)`**, а не `BETWEEN ... '23:59:59'`: не зависят от точности колонки
   (`DATETIME(3)`), соседние периоды стыкуются без дыр и двойного счёта.
6. **`LIKE 'abc%'` - диапазон, `LIKE '%abc'` - весь индекс.** Функциональный индекс (`INDEX ((DATE(created_at)))`)
   помогает, только если запрос нельзя переписать, и только для точно того же выражения.

| | Запрос | План | Прочитано строк | Время |
|---|---|---|---|---|
| Кампания 70, страница 501 | `OFFSET 10000` | `ref`, `idx_camp_created`, `Backward index scan` | 10 020 | ≈ 20-40 мс |
| То же, keyset | `created_at < c OR (created_at = c AND id < i)` | `range`, `key_len = 17` | 20 | ≈ 0,1 мс |
| Вся таблица, страница 50 001 | `OFFSET 1000000` | `ALL`, `Using filesort` | 2 000 000 | ≈ 1,2 с |
| То же, keyset | то же условие курсора | `range`, `idx_created`, без `filesort` | 20 | ≈ 1,5 мс |

Что вынести:
1. Цена `OFFSET N` растёт вместе с `N`: строки читаются и выбрасываются. Keyset стартует прямо с курсора, и цена страницы не зависит от глубины.
2. Курсор должен однозначно задавать позицию строки: `created_at` не уникален (у кампании 70 такое время встречается дважды), поэтому нужен тайбрейкер `id`. Курсор только по `created_at` теряет строку на границе страниц 509 и 510 (`id 919378`).
3. Условие курсора пишется через `OR`. Запись `(created_at, id) < (...)` короче, но в MySQL 8.0 диапазоном по индексу не становится: из индекса используется только `campaign_id` (`key_len = 4`), читается 10 020 строк, как у `OFFSET`; без фильтра по кампании - 1,9 млн строк, ≈ 5 с.
4. Отдельный индекс под `id` не нужен: InnoDB дописывает первичный ключ к вторичному индексу (`key_len = 17 = 4 + 5 + 8`). Оба столбца сортировки идут в одну сторону, поэтому `filesort` не нужен.
5. Цена keyset: нет перехода на произвольную страницу и общего числа страниц. Курсор отдаётся клиенту непрозрачной строкой и проверяется, а условие по кампании берётся на сервере.
